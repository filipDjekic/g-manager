# Station application-control policy

Stage 9 release target is Windows 10/11 Enterprise or Education with Application Identity/AppLocker available, a restricted standard customer account and NTFS game directories writable only by administrators/SYSTEM. Windows Server is supported for lab policy authoring, not as a gaming station. Home and unmanaged Pro machines are not supported release targets. WDAC may replace AppLocker after representative-hardware validation, but the Client process monitor is never the sole security boundary.

Each active profile must enumerate every launcher, concrete game and required helper executable. Allowing `steam.exe` does not implicitly allow Steam child games. Each executable has an absolute path and at least one publisher certificate, publisher subject or SHA-256 trust constraint; optional minimum file version prevents rollback. A dependency group links a launcher, its concrete games and helpers. Shell receives only launchable codes while Service resolves paths and arguments from the signed snapshot.

Generate a dedicated Ed25519 key pair outside the repository. Supply the Base64 PKCS#8 private key to backend as `STATION_POLICY_SIGNING_PRIVATE_KEY` and an immutable identifier as `STATION_POLICY_SIGNING_KEY_ID`. Put only the matching Base64 X.509/SPKI public key and key ID in the installed Service `Policy` configuration. Private keys must use the deployment secret store and must never enter source control or Client machines.

The Service verifies payload signature, key ID, station ID, executable trust and monotonically increasing configuration version. `apply-policy.ps1` records the original LOCAL AppLocker policy and exact owned rule GUIDs in a durable journal before mutation. Scoped deny rules target only the selected standard Windows player SID; exact application paths are excepted only while the customer is authenticated. Scripts/MSI remain denied for that account. Administrator accounts are not targets. Unrelated rules are preserved; Effective/domain policy is never imported into Local GPO. Existing AuditOnly rules are not silently enabled. Application paths must already be protected against nonprivileged writes; the Client rejects unsafe paths instead of rewriting game-folder ACLs. New deployments do not alter Chrome, WDAC or other Registry policies. Maintenance/removal subtract only owned rules and restore collection settings, with conflicts preserved for administrator resolution. Signed policy downgrade requires a new higher configuration version. Legacy global mutations without original backups cannot be safely inferred; restore them administratively before migration.

Policy authoring flow: create/update definitions in Stations, add every GAME/HELPER to the correct dependency group, inspect the effective-policy preview, assign the profile, then let the enrolled Service fetch `/api/v1/machine/configuration`. Deployment evidence for a release should include allowed launcher/game/helper execution, rejection of an unlisted child, tampered payload rejection, failed-update rollback and rejection of downloaded `.exe`, `.bat`, `.cmd` and `.ps1` files on the representative Windows target.

Local authorization, expiring maintenance, signed updates and emergency recovery are documented in [CLIENT_MANAGEMENT.md](docs/CLIENT_MANAGEMENT.md). Development never applies these Windows policies.
